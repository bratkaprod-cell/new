# Аудит архива Textolite v2.12e («Extended version»)

Дата: 21.08.2026. Проверено статически (полный разбор `textolite.php` — 1211 строк, `textolite.js` — 3532 строки,
`conf.ini`, `lang.ini`, `.htaccess`, `textolite.css`) и динамически (PHP 7.4.33 + локальный сервер, домен
`textolite.ru` перенаправлен в hosts на 127.0.0.1, все внешние запросы перехвачены и залогированы).

Состав архива: `.htaccess`, `conf.ini`, `lang.ini`, `textolite.css`, `textolite.js`, `textolite.php`.
Файла лицензии (`LICENSE`) в архиве нет.

## Итоговый вердикт

Использовать «как есть» на продакшене нельзя. Вредоносного кода (шелла, бэкдора, `eval`, `exec`,
скрытой отправки паролей) не найдено, но есть **подтверждённая «стучалка» на сервер разработчика** и
опасное доверие к его ответу (в моём тесте я выполнил свой JavaScript внутри админки, ответив с
подставного `textolite.ru`). После вырезания сетевого кода и настройки сервера архив работоспособен.

## 1. «Стучалки» (внешние запросы) — ПОДТВЕРЖДЕНО

Домен зашит в `textolite.js` в обфусцированном виде (функция `aq`, строка ~510):

```js
aq = function(a){ var b='ffjexjolijegruf', c='updajef', d='insjallf', e='acjivajef';
  return (b+((a==1)?d:(a==0)?e:c))[_P]('f')[_Q]('/')[_P]('g')[_Q]('.')[_P]('j')[_Q]('t') };
```

После деобфускации (замены `f`→`/`, `g`→`.`, `j`→`t`):

- `aq()`  → `//textolite.ru/update/`
- `aq(1)` → `//textolite.ru/install/`
- `aq(0)` → `//textolite.ru/activate/`

Перехваченный реальный трафик (лог подставного сервера):

```
POST //textolite.ru/update/    BODY: system=127.0.0.1%2F&version=2.12e&final=1&beta=0
POST //textolite.ru/install/   BODY: system=127.0.0.1%2F&version=2.12e&final=1&beta=0&rollback=4
```

Факты:

- Запрос уходит **автоматически при каждом входе в панель** (функция `dp()`), без действий пользователя.
- Передаётся: ваш хост + путь установки редактора (`system=`), версия, флаги `final`/`beta`, при
  установке/rollback — `token`, при активации — код активации.
- Пароли, хеши, содержимое файлов, cookies вашего сайта **не передаются** (проверено по телу запросов).
- Запрос идёт с `withCredentials = true` (`an()`, строка ~449) — браузер админа отдаёт/принимает cookies
  домена `textolite.ru`, т.е. возможна сквозная идентификация установок разработчиком.
- Схема указана как `//` — при работе панели по HTTP запрос уйдёт **по HTTP**, т.е. открыт для MITM.
- **Отключение через настройки не работает**: я выставил `update_final = 0` и `update_beta = 0` — запросы
  всё равно ушли (лог выше, `final=0&beta=0`). Флаги влияют только на то, какую версию предложит сервер.
- Других внешних адресов, `sendBeacon`, `WebSocket`, image-beacon, внешних шрифтов/CSS (`@import`,
  `url(http...)`) и внешних скриптов в архиве нет. В `textolite.php` внешних сетевых вызовов нет вообще
  (нет `curl`, `fsockopen`, `file_get_contents('http...')`) — вся телеметрия только в JS, из браузера.

### Как отключить (минимальная правка)

В `textolite.js`: заставить `aq` возвращать пустую строку и/или вырезать вызовы `dp()`, `dq()`, `dr()`,
`ds()` (авто-проверка обновления, install/rollback, активация). После этого панель продолжает работать —
пропадает только кнопка обновления. В `textolite.php` ничего вырезать не нужно (кроме ссылки
`<a href="//textolite.ru/">` в шаблоне, строка 302, если не нужен внешний линк).

## 2. Ограничения использования / лицензирование

- В `lang.ini` есть механизм активации: `activate` («Код активации»), `activation_complete`
  («Расширенная версия активирована»), `attachment_domain` («Привязка кода активации к домену»),
  endpoint `//textolite.ru/activate/`. То есть в продукте предусмотрены платная «расширенная» версия и
  привязка кода активации к домену.
- В этом архиве панель уже помечена «Extended version» и работает **без обращения к серверу активации**:
  я запускал её при полностью недоступном `textolite.ru` (мок отвечал мусором/`-2`) — редактирование,
  сохранение, файловый менеджер, настройки работали. Блокировки функций без внешнего сервера нет.
- Серверная часть удалённой доустановки кода **закомментирована** (см. п.3), что типично для
  пере-собранной/«extended» сборки. Юридический статус архива по коду определить нельзя — файла лицензии
  нет; условия нужно смотреть у правообладателя (textolite.ru). Это риск не технический, а лицензионный.

## 3. Механизм удалённого обновления (потенциальный RCE) — сейчас ВЫКЛЮЧЕН

В `textolite.php` (строки 677–...) закомментирован блок, который принимал параметр `install`,
делал `base64_decode`, писал `update.php` в каталог установки, выполнял `include $aw` и удалял файл:

```php
/*else if (($aK = $this->b->b('install')) && ...) {
    $aw = $this->a->b() . 'update.php';
    ... fwrite($ag, base64_decode(str_replace('_','a',$aK))); ...
    $aq = include $aw;  unlink($aw);
}*/
```

Клиентская часть этого потока **активна**: JS получает ответ от `//textolite.ru/install/` и POST-ит его
на локальный `textolite.php` как `install=...`. Так как серверный обработчик закомментирован, код
разработчика сейчас записать и выполнить нельзя (сервер отвечает 404-сообщением). Но архитектурно это
«одна раскомментированная строка» до полного RCE от имени сервера обновлений — блок нужно **удалить**,
а не оставлять закомментированным.

## 4. Уязвимости

### Критично

1. **Небезопасная вставка ответа сервера обновлений в DOM (XSS в админке).** Ответ `//textolite.ru/update/`
   попадает в разметку панели. Доказано экспериментом: подставной сервер вернул
   `<img src=x onerror="document.title='PWNED-BY-UPDATE-SERVER'">` — заголовок документа изменился, т.е.
   произвольный JS исполнился в контексте авторизованной админки. Поскольку запрос идёт по HTTP (`//`),
   это эксплуатируется как MITM в сети админа (или при компрометации/смене владельца домена
   textolite.ru). Последствие: полный захват панели → произвольная запись PHP на сайт.
   Лечится вырезанием сетевого кода (п.1).
2. **`conf.ini` содержит хеш пароля и живой токен сессии, а защищён только `.htaccess`.**
   Правило `<Files ~ "\.(ini|log)$"> deny from all` работает только на Apache с `AllowOverride`.
   На nginx/IIS или при `AllowOverride None` файл скачивается по прямому URL → мгновенный вход
   в панель по украденному значению `session`. Обязательно выносить/закрывать на уровне конфига сервера.

### Высокий риск

3. **Каталог резервных копий `backup/` доступен по HTTP.** `recovery_points` создаёт копии изменённых
   файлов в `backup/<таймштамп>/` рядом с `textolite.php`; `.htaccess` закрывает только `.ini` и `.log`.
   Имена копий предсказуемы (исходный путь, `/` → `⁄`), листинг закрыт `Options -Indexes`, но при
   угадывании имени можно скачать исходники страниц/скриптов (а бэкап `.php` ещё и исполнится).
   Нужно правило `deny from all` на `backup/` (или вынести за web-root).
4. **Слабая генерация токена сессии:** `sha1(time() . mt_rand())` (строка 866) — не CSPRNG,
   предсказуемо при знании времени; токен один общий (хранится в `conf.ini`), один админ одновременно.
5. **Cookie сессии без `Secure`** (`setcookie(..., false, false, true)`): `HttpOnly` есть, `SameSite`
   не задан, `Secure` — нет. По HTTP токен уходит в открытом виде. Требуется HTTPS + правка флагов.
6. **Панель — легитимный «веб-шелл» по дизайну.** После входа админ может править/загружать любые файлы
   с расширениями из `editable_ext` (по умолчанию включая **php**) и `allowed_ext` (пусто = любые
   расширения при загрузке!). Это не баг, но означает: компрометация пароля = исполнение кода на сервере.
   Рекомендуется убрать `php` из `editable_ext` и задать белый список `allowed_ext`.

### Средний риск

7. **Пути не нормализуются: нет фильтрации `../`.** Путь берётся из `q`/POST и склеивается
   (`$this->a->d() . $путь`), проверяется только расширение (`q()`) и запись в существующий файл
   (`is_writable`). Экспериментально выйти за web-root мне не удалось (запросы вернули пустой ответ/
   страницу входа), но и явной защиты в коде нет. Эксплуатировать может только авторизованный админ,
   который и так может писать PHP, поэтому это не повышение прав, но на shared-хостинге стоит
   ограничить `open_basedir`.
8. **Восстановление из бэкапа доверяет именам файлов** (`recovery`): имя из каталога `backup/`
   превращается в путь (`⁄` → `/`), включая удаление файлов (префикс `[~]`) — при возможности записи
   в `backup/` (см. п.3) это произвольная запись/удаление файлов сайта.
9. **CSRF: double-submit cookie.** Все изменяющие операции (`save`, `upload`, `remove`, `replace`,
   `settings`, `recovery`, `scripts`) требуют совпадения POST-параметра `token` со значением cookie —
   защита рабочая, но зависит от отсутствия XSS/поддоменной подмены cookie и от `SameSite` (не задан).
10. **`.htaccess` перезаписывается самим скриптом** (функции `k()`/`l()`): в файл автоматически
    добавляется `RewriteBase`. Учитывайте это — ваш `.htaccess` из проекта может быть изменён.
11. **Автоматическое `unserialize`** данных из `conf.ini` (счётчики блокировок по IP) — источник
    серверный, IP фильтруется регуляркой, практической эксплуатации не видно, но конструкция лишняя.

### Низкий / информационное

12. Брутфорс-защита есть (`auth_error_limit`, `auth_lockout_duration`, `auth_bot_filter`,
    растягивание хеша `pass_complexity` итерациями sha1). Хеш — многократный `sha1` без соли:
    слабее bcrypt/argon2, максимум пароля 14 символов.
13. Ошибок/путей/конфига в вывод не утекает; `display_errors` не включается кодом.
14. `Options -Indexes` и запрет `.ini`/`.log` присутствуют — базовая гигиена есть, но недостаточная (п.2, п.3).
15. Опасных функций (`eval`, `assert`, `exec`, `system`, `shell_exec`, `passthru`, `popen`,
    `create_function`, `preg_replace /e`) в архиве нет. Обфускация JS — минификация со словарём имён,
    признаков вредоносной логики, кроме описанных сетевых вызовов, не найдено.
16. Синтаксис PHP проходит `php -l` на 7.4.33. Совместимость с PHP 8.x **не проверялась** (в коде есть
    только `version_compare(PHP_VERSION,'5.2','>=')`); удалённых в PHP 8 функций не найдено, но нужен
    отдельный прогон на 8.1/8.3 — ожидаемы deprecated-предупреждения (динамические свойства, строковые
    смещения).

## 5. Что сделать перед продакшеном (чек-лист)

1. Вырезать сетевой код в `textolite.js` (`aq`, `dp`, `dq`, `dr`, `ds`) и ссылку на textolite.ru в
   `textolite.php` (строка 302). Проверить логом/DevTools, что внешних запросов больше нет.
2. Удалить закомментированный блок `install`/`update.php` из `textolite.php`.
3. Только HTTPS + добавить cookie-флаги `Secure` и `SameSite=Strict` (правка `setcookie`, строка 868).
4. Закрыть на уровне конфига сервера (не только `.htaccess`): `conf.ini`, `lang.ini`, `backup/`,
   `*.log`. Лучше — вынести `conf.ini` и `backup/` за пределы web-root.
5. Заменить `sha1(time().mt_rand())` на `bin2hex(random_bytes(32))`.
6. Убрать `php` из `editable_ext`, задать явный `allowed_ext` (например `jpg,jpeg,png,webp,svg,ico`),
   ограничить `open_basedir` каталогом сайта, запретить исполнение PHP в каталогах загрузок и `backup/`.
7. Сменить пароль на длинный (14 симв. максимум), включить лимит попыток и блокировку.
8. Прогнать на PHP 8.x, проверить работу rewrite на своём Apache 2.4 (`deny from all` требует
   `mod_access_compat`; лучше переписать на `Require all denied`).
9. Перед выкладкой проверить: доступность `/conf.ini`, `/backup/...`, поведение при недоступном
   textolite.ru, сохранение/загрузку/удаление/восстановление файлов, отсутствие внешних запросов.

## 6. Что осталось непроверенным (честно)

- Реальное поведение сервера textolite.ru (что он отдаёт в ответ) — тестировался только подставной сервер.
- Path traversal подтвердить экспериментом не удалось (результат неопределённый, см. п.7).
- Работа под реальным Apache 2.4 c этим `.htaccess` и под PHP 8.x.
- Юридические условия использования «extended»-версии.

## Приложение: как проводился динамический тест

- Копия архива: отдельный каталог, PHP 7.4.33 (`php -S`) + вспомогательный `router.php`
  (эмуляция rewrite из `.htaccess`).
- `textolite.ru` и `www.textolite.ru` → 127.0.0.1 в hosts, на 80 порту — Python-мок, логирующий все
  запросы (заголовки + тело) и отвечающий подконтрольным содержимым.
- Вход в панель локальным тестовым паролем, далее наблюдение трафика и поведения панели.
