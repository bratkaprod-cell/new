# Аудит №2: сайт SiteRescue24 (v8) + CMS Textolite (патченная копия)

Дата: 2026-08-21. Окружение проверки: PHP 7.4.33 (встроенный сервер + router.php), Windows.
Первый отчёт (стучалки Textolite и их удаление) — `docs/textolite-audit.md`. Здесь — то, что найдено дополнительно.

## 1. Сайт (index.html, *.html, assets/, build.py, .htaccess)

Сайт полностью статический: серверного кода нет, форм-обработчика нет, БД нет. Классических
серверных уязвимостей (SQLi, RCE, LFI, загрузка файлов) в нём быть не может.

| # | Уровень | Проблема | Детали |
|---|---------|----------|--------|
| 1 | Функциональный дефект (высокий приоритет) | Формы заявок никуда не отправляются | `assets/main.js`: `submit` → `preventDefault()` и просто показывается «Заявка отправлена ✓» / модалка «Заявка принята!». Данные клиента не уходят ни на почту, ни в Telegram — все лиды теряются. Нужен бэкенд (PHP-скрипт + отправка в Telegram/на email) или сторонний сервис. |
| 2 | Средний (приватность / 152-ФЗ, GDPR) | Внешние ресурсы Google Fonts | В `<head>` подключаются `fonts.googleapis.com` и `fonts.gstatic.com` — IP и User-Agent каждого посетителя уходят Google. Это «стучалка» уровня приватности. Лечится самостоятельным хостингом шрифтов (`assets/fonts/`) + удалением внешних доменов из CSP. |
| 3 | Средний | HTTPS не форсируется, нет HSTS | В `.htaccess` блок редиректа на HTTPS и `Strict-Transport-Security` закомментированы. После установки SSL нужно раскомментировать, иначе часть трафика (и cookie CMS) идёт по HTTP. |
| 4 | Низкий | CSP допускает `style-src 'unsafe-inline'` | Из-за инлайновых стилей в разметке. Ослабляет защиту от XSS-инъекций стилями; не критично для статики, но при добавлении бэкенда стоит убрать. |
| 5 | Низкий | Антиспам-защита форм только на клиенте | Honeypot, задержка 3 сек и лимит 3 заявок/10 мин живут в JS и `localStorage` — бот их обходит. Валидацию и лимиты обязательно дублировать на сервере, когда появится обработчик формы. |
| 6 | Информационно | Заглушки в контенте | Телефон `+7 900 000-00-00`, `t.me/your_tg`, `vk.com/your_vk`, `max.ru/your_max`, ссылки «Политика конфиденциальности / Договор-оферта / Реквизиты» ведут на `#`. Для приёма реального трафика (и требований ФЗ о персональных данных) нужны реальные значения и страница политики. |
| 7 | Информационно | `build.py` безопасен | Шаблоны собираются из константных данных внутри файла, пользовательский ввод не участвует — инъекций в генерацию нет. Сам `build.py` закрыт от скачивания правилом `<FilesMatch "\.(py|md|log|bak|env|ini|sh)$">`. |

## 2. CMS Textolite — дополнительно найденные уязвимости

Всё ниже относится к коду, который остался после удаления «стучалок». Ключевой момент: почти все
находки — это повышение ущерба от одного скомпрометированного пароля админки: у Textolite нет
разделения прав, файловый менеджер работает от имени веб-сервера.

| # | Уровень | Проблема | Статус |
|---|---------|----------|--------|
| 1 | Критический | В поставке `conf.ini` лежал готовый хеш пароля и валидный `session` из архива вендора. Кто знает пароль этой сборки — входит в вашу админку сразу после установки. | **Исправлено**: `password`, `session`, `auth_time` очищены — пароль задаётся при первом входе. |
| 2 | Критический | `allowed_ext` в поставке пустой, а проверка `q()` при пустом значении возвращает `true` **для любого расширения** → через файловый менеджер можно загрузить `.php`/`.htaccess` и получить выполнение кода на сервере. | **Исправлено**: `allowed_ext` заполнен безопасным списком (html, css, js, json, xml, txt, изображения, шрифты, pdf, видео) — без `php`. |
| 3 | Высокий | Regex-инъекция в whitelist расширений: расширение файла подставлялось в шаблон `preg_match` без экранирования (`'~(?:^|,\s*)' . $a . '(?:\s*,|$)~i'`). Проверено на PHP 7.4: расширения `x|php`, `[a-z]+`, `.*`, `ph.` проходят проверку, хотя в списке их нет — т.е. whitelist обходится именем файла. | **Исправлено**: расширение экранируется через `preg_quote($a, '~')`. |
| 4 | Высокий (по дизайну) | `editable_ext` и `visual_ext` по умолчанию включают `php` → авторизованный пользователь может редактировать и создавать PHP-код сайта из браузера. Это штатная функция Textolite, но фактически это RCE-по-паролю. | Не менял (ломает функциональность). Рекомендация: убрать `php` из `editable_ext`/`visual_ext`, если вы правите только HTML/CSS. |
| 5 | Высокий | Единственный фактор защиты — один пароль в `conf.ini`; нет 2FA, нет привязки к IP. Лимит попыток (`auth_error_limit = 5`, блокировка 1 мин) слабый для офлайн-неограниченного перебора через ботнет. | Рекомендация: закрыть каталог CMS вторым слоем — Basic-auth Apache (`.htpasswd`) или разрешить доступ только со своих IP. |
| 6 | Средний | `conf.ini` (хеш пароля + активный токен сессии) и каталог точек восстановления лежат внутри веб-корня; защищены только `.htaccess`. При смене хостинга/веб-сервера (nginx) или ошибке конфигурации файл отдаётся по HTTP. | Частично закрыто в нашем `.htaccess` (запрет `.ini`/`.log`, `backup/`, `Options -Indexes`). Полноценное решение — вынести CMS и её данные за пределы `public_html`, что требует переписывания путей. |
| 7 | Средний | Cookie сессии без флагов `Secure` / `HttpOnly` / `SameSite` — перехват по HTTP или XSS на сайте даёт доступ к админке. | Не менял (правка требует переработки cookie-слоя). Минимум: включить принудительный HTTPS + HSTS. |
| 8 | Средний | Точки восстановления (`recovery_points = 5`) хранят копии страниц сайта в подкаталоге с именем-датой. Если правило `.htaccess` не применится, содержимое (в том числе черновики и удалённый контент) читается по прямой ссылке. | Закрыто правилом `RedirectMatch 404 (?i)(^|/)backup/`; проверьте фактическое имя каталога на своём хостинге после первой правки страницы и при необходимости добавьте его в `.htaccess`. |
| 9 | Низкий | Токен сессии раньше генерировался как `sha1(time() . mt_rand())` — предсказуемо. | **Исправлено ранее**: `random_bytes(20)` (см. первый отчёт). |
| 10 | Не подтверждено | Path traversal в save/remove/upload: пути строятся склейкой строк, но перед записью вызывается проверка `_a()` и сравнение с DOCUMENT_ROOT. Мои попытки выйти за корень (`../secret_outside.txt`, `..%2F…`, `..\..\…`) содержимое файла вне веб-корня не вернули. Полноценная проверка требует реального Apache 2.4 + mod_rewrite и авторизованной сессии; на встроенном сервере PHP поведение маршрутизации отличается. | Требует проверки на реальном хостинге до продакшена. |

## 3. Что исправлено в этом коммите

- `cms/textolite/textolite.php` — `preg_quote()` в проверке расширений (устранена regex-инъекция).
- `cms/textolite/conf.ini` — удалён чужой хеш пароля и токен сессии, заполнен `allowed_ext` без `php`.
- Проверено: `php -l` без ошибок; панель открывается, показывает форму авторизации (пароль задаётся заново); внешних запросов к textolite.ru нет (лог перехватчика пуст).

## 4. Чек-лист перед продакшеном

1. Задать длинный пароль при первом входе в панель (12+ символов).
2. Поставить CMS **в отдельный каталог**, не в корень сайта: у CMS свой `.htaccess` с `RewriteRule` на `textolite.php`, в корне он перехватит все запросы сайта.
3. Включить HTTPS + раскомментировать HSTS и редирект в корневом `.htaccess`.
4. Закрыть каталог CMS Basic-auth или по IP.
5. Убрать `php` из `editable_ext`/`visual_ext`, если PHP-файлы через панель не редактируются.
6. Сделать бэкенд для форм заявок (сейчас лиды не отправляются) с серверной валидацией и антиспамом.
7. Заменить Google Fonts на локальные шрифты.
8. Заполнить реальные контакты и опубликовать политику обработки персональных данных.
9. После первой правки страницы проверить по HTTP: `/<путь-к-cms>/conf.ini` и каталог точек восстановления должны отдавать 403/404.
